# 3. Init-client scaffolding workflow and string match guard

Date: 2026-09-05

## Status

Accepted (2026-09-05). Implemented in the same change.

## Context

After `init-client`, step B1c of SETUP.md required manual copying of three doc templates (`intake-template.md`, `handoff-template.md`, plus the `docs/reinit-checklist.md` generated by the script itself). This was an untracked manual checklist rather than part of the scaffolding automation, creating an operator burden and a chance for omission on each new client.

Separately, the self-identity string matches in the `REPLACEMENTS` array proved fragile. When SETUP.md was reworded in commit 3a08f2d ("fix: repair init-client string matches..."), the `replaceInFile` function only warned when a string was not found (e.g., "not found in SETUP.md (skipped)"); there was no gate to catch the breakage until someone ran `init-client` and noticed the warning, a failure mode with a long detection latency.

## Decision

1. **Font-mode prompt default**: extend ADR 0002 item 1 (which documented the system-font path) by making `system` the enter-key default in the font-mode prompt. Rationale: matches the `[default]` convention used in other prompts, keeps piped runs working (like the test harness, which sends a newline), and the do-nothing path ships no fetched web font, which is simpler and faster on first build.

2. **Scaffolded intake and handoff templates**: `init-client` now calls a `scaffold` helper that copies `docs/intake-template.md` to `docs/intake.md` and `docs/handoff-template.md` to `docs/handoff.md` if they do not exist. The generated `docs/reinit-checklist.md` remains part of the script. Rationale: every new client repo needs these docs in place; bundling the copy as part of `init-client` removes a manual step.

3. **`docs/go-live.md` not templated**: this is a fixed launch runbook meant for every client, not a per-client fill-in-the-blanks doc. `init-client` ships it to the client repo as-is: it is not copied to a working name and not templatized. Rationale: consistency across all Dodai client launches, and avoiding the bookkeeping burden of maintaining a copy of the same checklist per client.

4. **`REPLACEMENTS` table as single source of truth for verbatim matches**: every string that `init-client` rewrites is declared in the `REPLACEMENTS` array. The `node scripts/init-client.mjs --check` command gated on the `.template-repo` marker (wired into `npm run check`) verifies that each `from` string still exists in its target file, exiting with status 1 if any are missing. This is the guard against silent match drift. Rationale: future doc rewordings fail the check until the `REPLACEMENTS` literal is updated in the same commit, making the breakage immediate and visible.

5. **`docs/reinit-checklist.md` as tracked B4 input**: the script writes the reinit checklist as part of `init-client`. SETUP.md remains the canonical explained version of the B4 checklist items, kept in sync by hand. Rationale: B4 is the checklist after scaffold; SETUP.md explains the work step by step. Keeping both in sync is manual discipline, but the script ensures a new client gets a usable checklist out of the box.

## Consequences

- Any future doc reword near a matched string fails `npm run check` until the `REPLACEMENTS` literal is updated in the same commit. Breaking the check is intended.
- `scripts/init-client.mjs` is now the one place all verbatim matches live, reducing the risk of drift between what the script was coded to match and what the template actually contains.
- A fresh fork after `init-client` has working docs (intake, handoff, reinit checklist) and a fixed launch reference (go-live) in place with no manual copying of templates by the operator.
- The system-font default aligns the font-mode prompt with the `[default]` convention and makes piped runs (including tests) work without special casing.
